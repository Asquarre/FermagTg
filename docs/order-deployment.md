# Заказы на Vercel без Redis

Используются существующие Google Sheets и Telegram. Redis, дополнительная база, отдельный технический лист и планировщик не нужны.

## Публикация

В Production нужны четыре серверные переменные: `GOOGLE_SHEETS_CREDENTIALS`, `GOOGLE_SHEETS_ID`, `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`. Сборка запускается из корня через `npm run build`, Node.js 22+. Отсутствие переменных останавливает production-сборку. `vercel.json` включает JSON-каталог в серверные функции.

Ранее подключённые Redis-переменные и `CRON_SECRET` больше не читаются. Их наличие не мешает сайту. Удалять облачную базу или интеграцию для публикации не требуется; код сам ничего в аккаунтах не удаляет.

## Как обрабатывается заказ

1. Браузер сохраняет снимок отправляемого заказа и UUID до первого сетевого запроса. Перезагрузка и повторная попытка используют тот же UUID.
2. Сервер ищет скрытую служебную метку этого заказа в Google Sheets. Если лист уже готов, возвращает подтверждение, не создаёт второй лист и не отправляет повторное сообщение.
3. Для нового заказа проверяет товары и цены по каталогу. Создание листа, запись данных и формул, оформление и служебные метки выполняются одним атомарным запросом. Внутренний числовой ID листа вычисляется из UUID одинаково на всех процессах, поэтому параллельные запросы не могут создать два листа с одним ID.
4. Только запрос, который получил успешный ответ на создание листа, отправляет Telegram. Сообщение до 4096 символов остаётся в исходном формате. Более длинное разбивается преимущественно по границам строк на пронумерованные части с сохранением всех товаров и их порядка. Части отправляются последовательно с общим лимитом времени 20 секунд. При ошибке отправка останавливается; повтор запроса не пересылает уже отправленные части, оформленный лист сохраняется. Поэтому при сбое Telegram сообщение может прийти не полностью.
5. Успех для покупателя означает, что данные и оформление листа подтверждены. Ошибка Telegram не превращает готовый заказ в ошибочный и не заставляет повторять весь заказ.

UUID и отпечаток состава записываются в developer metadata листа, а не в ячейки, название листа или Telegram. Отдельного технического листа нет. Удаление меток или готовых листов нарушает проверку повторов. Если вычисленный ID совпал с посторонним листом, сервер откажется записывать заказ вместо перезаписи чужих данных; потребуется разбор по логам. Этот редкий случай намеренно не обходится генерацией нового ID, иначе возникнет риск дублей.

## Ограничения

- После закрытия сайта нет фонового продолжения незавершённой отправки. Открытие сайта снова продолжит проверку запроса, пока он сохранён в браузере.
- При сбое Telegram или потере ответа Google после успешной записи заказ останется в оформленном листе, но сообщение Telegram может не прийти. Автоматической повторной отправки такого сообщения нет. Логи Vercel отмечают эти случаи по внутреннему ID, без токенов и персональных данных.
- Если браузер полностью очищен до подтверждения, он потеряет связь со своим запросом. Новый осознанный заказ получает новый ID, даже если корзины одинаковые.
- Защита действует на повтор одного ID, а не на любые одинаковые корзины разных заказов.

## Проверки

`npm run test:orders` проверяет атомарную запись, одновременные запросы, потерю ответа, ошибку оформления, сбой Telegram и неизменность ID на подменённых сервисах. `npm test -- --watchAll=false` проверяет браузерное сохранение запроса и статусы. `npm run dev` работает только с локальными JSON-файлами, внешние сервисы не подключает.

Доступ к реальным аккаунтам проверяется отдельно на тестовой таблице/чате. Успешные локальные тесты не подтверждают действительность production-ключей.
